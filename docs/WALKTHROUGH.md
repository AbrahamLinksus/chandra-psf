# Codebase walkthrough — Chandra Honda PSF, phase 2 (production) with questionnaire v2

> A guided tour for a new developer: understand, own and explain this code. Pairs with `docs/ARCHITECTURE.md` (what and why), `docs/LLD-phase2.md` (phase-2 reference sections §15–§27) and `docs/LLD.md` (phase-1 sections still in force). Line numbers are as built at handover and may drift by a few lines.

## 1. Read these first (in order)
1. `docs/ARCHITECTURE.md`: the diagram and component table; five minutes to know where everything lives.
2. `src/data/access/index.ts`: the `DataAccess` interface, the one seam between screens and data. Everything a screen can ask for is here, one interface per repo in `src/data/access/repos/`.
3. `src/data/access/result.ts`: `Result<T>`, `ErrorCode`, `StepUp`. Repo methods never throw; they return these, in the browser and on the server.
4. `src/domain/types.ts` and `src/domain/questionnaire.ts`: the data shapes and the whole questionnaire as data. Since CR-2 that is `QUESTIONNAIRE_V2` only: ten base questions Q1–Q10 in six steps (Q1 overall service, Q2 complaints rectified, Q3 issues after delivery, Q4 advisor behaviour, Q5 on time, Q6 good condition, Q7 charges explained, Q8 charges affordable, Q9 recommend, Q10 callback, always last) and their follow-ups (Q1a, Q2a, Q3a, Q4a, Q5a, Q6a, Q8a, Q9a, Q10a time slot from `CALLBACK_SLOTS`); rating follow-ups open on 1–2. Mapping from v1 codes: `docs/LLD-phase2.md` §17.6.
5. `src/domain/visibility.ts` and `src/domain/alertRules.ts`: the business rules (which follow-ups show, which answers are allowed, when an alert exists), pure and unit-tested.
6. `src/app/providers.tsx` (browser wiring) and `src/server/createServerDataAccess.ts` (server wiring): the two composition roots.
7. `src/server/rpc/handler.ts` (`handleRpc`) and `src/server/rpc/index.ts` (`rpcTables`): the only door between them. Every call is checked here.
8. `src/server/ctx.ts` (`RequestCtx`, `guard`) and `src/server/scope.ts` (`requireAdmin`, `branchFilter`): what every server repo method starts with.
9. `src/server/repos/feedback.ts`: a complete server repo, short enough to read in one sitting.
10. `src/features/admin-users/` (`src/features/admin-users/UsersScreen.tsx`, `src/features/admin-users/useUserList.ts`, `src/features/admin-users/AddUserForm.tsx`) with `src/server/repos/users.ts` and `src/server/rpc/users.ts`: a complete feature from screen to database, the pattern to copy.
11. `docs/SPEC.md` for the product rules, `docs/CONVENTIONS.md` for the coding rules, `docs/DEPLOY.md` for running it.

## 2. Follow one request end to end
**Trace: a customer submits feedback with a low rating and a callback request, and the admin's Alerts badge changes.**

The same journey runs end to end in `tests/e2e/walkthrough/walkthrough.spec.ts`: the customer answers Q1 = 1 and Q10 = Yes with the Evening slot (`fillUntilCallback`, `answerCallback` in `tests/e2e/walkthrough/helpers.ts`), the thank-you page says "Our team will call you: Evening 3 PM–6 PM" (`src/features/feedback-form/ThankYouView.tsx`), the alert lists the callback slot first (`evaluateAlertReasons` in `src/domain/alertRules.ts`), and the Overview shows the step 9 tiles and category rows.

1. **Wiring (once per page load).** `src/app/providers.tsx` `createClientDataAccess` (line 20) builds an activity tracker (`createActivityTracker`, `src/data/remote/activity.ts`), a poller (`createPoller`, `src/data/remote/poller.ts`) and `createRemoteDataAccess` (`src/data/remote/createRemoteDataAccess.ts`), which turns every repo method call into `rpc` (`src/data/remote/rpcClient.ts`, line 31). `DataAccessProvider` (`src/data/access/provider.tsx`) hands it to React.
2. **Open the link.** `src/app/f/[token]/page.tsx` renders `FeedbackFormScreen` (`src/features/feedback-form/FeedbackFormScreen.tsx`). `useFormContext` (`src/features/feedback-form/useFormContext.ts`) calls the feedback repo's `getVisitByToken` with the link code, i.e. a POST to /api/rpc/feedback/getVisitByToken.
3. **The RPC door.** `src/app/api/rpc/[repo]/[method]/route.ts` calls `handleRpc` (`src/server/rpc/handler.ts`, line 94): same-origin JSON check, `findRpcEntry` (unknown method → 404), zod arguments from the registry (`src/server/rpc/feedback.ts`, `src/server/rpc/args.ts`), then `run`: `buildBaseCtx` and `withSession` (`src/server/rpc/context.ts`), the per-IP public flood limit (`hitIpLimit`, `src/server/rateLimit.ts`) because the customer has no staff session, and `dispatch` into `createServerDataAccess(ctx)`.
4. **Resolve the link.** `ServerFeedbackRepo.getVisitByToken` (`src/server/repos/feedback.ts`, line 130): `linkExists` (unknown codes get no counter row), `hitLinkLimit` (30 opens per hour per link), `resolveLink` (line 63: cancelled or erased → invalid, completed, replaced or past expiry → expired, else ready). Ready returns the customer's details and `QUESTIONNAIRE_V2`; other states render `LinkStateScreen`.
5. **Fill the form.** `FeedbackFlowScreen` calls `useFeedbackFlow` (`src/features/feedback-form/useFeedbackFlow.ts`, line 80). Its effect calls `markOpened` (line 86), so link-preview robots never mark a link opened. Each tap dispatches into `formReducer` (`src/features/feedback-form/formMachine.ts`) and `saveDraft` (line 90, `src/features/feedback-form/draft.ts`) keeps the answers per visit. `StepView` shows `visibleQuestions` from `src/domain/visibility.ts`, so a rating of 1 reveals its follow-up.
6. **Submit.** The flow's mutation (`useRepoMutation`, `src/hooks/useRepoMutation.ts`) calls `submitFeedback` (`src/features/feedback-form/submitFlow.ts`, line 18) with `submissionIdFor(visitId)`, one id per visit kept for every retry. That calls the feedback repo's `submitResponse` and maps the `Result` to a submit outcome.
7. **Server repo.** `ServerFeedbackRepo.submitResponse` (line 167) inside `guard`: link exists, submit limit (5 per hour), `resolveLink` (completed → `replay`, which returns the first result again for the same submission id), `findStrayAnswers` (v1 codes or hidden follow-ups → VALIDATION), `validateSubmission`. Then one transaction in `store` (line 198): claim the visit with a guarded UPDATE (a lost race goes to `afterLostRace`), insert the response with questionnaire version 2, and `raiseAlert` (line 236): `evaluateAlertReasons` + `reconcileAlert(null, …)`, insert the alert, `writeAudit` (`src/server/audit.ts`) an alert.create row with the System actor. The reply is `callbackOf(answers)`, which drives `ThankYouView` (`slotLabel` from `src/domain/alertRules.ts`).
8. **Refresh.** In the admin's browser `createPoller` emits `STAFF_TOPICS` every poll interval while the tab is visible and in use and a staff session is cached; `useLiveInvalidation` (`src/hooks/useLiveInvalidation.ts`) invalidates every query.
9. **The admin sees it.** `useOpenAlertCount` (`src/hooks/useOpenAlertCount.ts`) re-runs the alerts repo's `countOpen`, i.e. `ServerAlertRepo.countOpen` (`src/server/repos/alerts.ts`, line 78), scoped by `requireAdmin` and `branchFilter`, counting only alerts of live responses. `AdminShell` (`src/components/shared/AdminShell.tsx`, line 16) renders the badge. The Overview's open-alerts tile uses the same rule in `ServerAnalyticsRepo` (`src/server/repos/analytics.ts`).
10. **The Overview (D-47).** `src/app/admin/page.tsx` → `AdminOverviewScreen` (`src/features/admin-overview/AdminOverviewScreen.tsx`) → `useOverview` → the analytics repo's `getAnalytics`, which on the server (`ServerAnalyticsRepo.getAnalytics`, `src/server/repos/analytics.ts`) loads the period and the previous one and returns `computeOverview` (`src/domain/metrics/overview.ts`). `KpiTiles` shows six tiles in words: Avg overall satisfaction (Q1), Recommend rate (Q9 % Yes), Responses, Response rate, **Callbacks requested** (responses with Q10 = Yes) and Open alerts; the first five carry a change arrow vs the previous period. `CategoryScores` lists the five categories with a score /100 (`buildCategories`, `src/domain/metrics/categories.ts`); each row is a collapsed button that expands into `QuestionBars`: every question by its wording with its answer counts and its follow-up's option counts underneath. `AdvisorTable` ranks advisors by `advisorScore` (`src/domain/metrics/advisorScore.ts`): each answer scored 0–100 (rating (r − 1) ÷ 4 × 100, Yes 100 / No 0, Q2 Partially 50), averaged per question over the advisor's responses, then weighted Q4 30 · Q1 20 · Q2 15 · Q7 10 · Q5 10 · Q6 10 · Q9 5 (`ADVISOR_WEIGHTS`) and divided by the weights of the questions that have answers, rounded to a whole number; fewer than 3 responses shows "—".

## 3. How the layers fit
| Layer | Folder | May import | Never imports |
|---|---|---|---|
| Pages | `src/app/` (not `src/app/api/`) | features, shared components | `src/server/`, `src/data/remote/` (except `src/app/providers.tsx`) |
| Features | `src/features/<name>/` | `src/components/shared/`, `src/hooks/`, `src/data/access/`, `src/domain/` | other features, `src/data/remote/`, `src/server/` |
| Shared UI and hooks | `src/components/shared/`, `src/hooks/` | `src/data/access/`, `src/domain/` | features, app, server |
| Contract | `src/data/access/` | `src/domain/` | remote, server, features, components |
| Remote client | `src/data/remote/` | `src/data/access/`, `src/domain/` | features, components, server |
| API routes | `src/app/api/` | `src/server/` (not `src/server/repos/`) | features, components |
| Server | `src/server/` | `src/domain/`, types and `Result` from `src/data/access/` | features, components, hooks, React |
| Server repos | `src/server/repos/` | server core, domain | imported only by `src/server/createServerDataAccess.ts` |
| Domain | `src/domain/` | zod only | everything else |

The direction is inward: screens → hooks → the `DataAccess` interface → domain, and on the server: route → RPC handler → server repos → domain and database. These rules are enforced by `.dependency-cruiser.cjs` and by ESLint's import bans in `eslint.config.mjs` (database driver, Drizzle and argon2 only under `src/server` and `scripts`), both run by `scripts/check.sh`; you cannot merge a violation. `tests/unit/server/rpc/layers.test.ts` proves the rules fire. Roles are enforced inside every server repo (`requireStaff`, `requireAdmin`, `scopeOf`, `branchFilter` in `src/server/scope.ts`); `src/proxy.ts` and `RoleGuard` (`src/components/shared/RoleGuard.tsx`) only redirect for a good user experience.

|---|---|---|
| add an admin screen | new `src/features/admin-<name>/`, new `src/app/admin/<name>/page.tsx`, one entry in `ADMIN_NAV` (`src/components/shared/adminNav.ts`) | `src/features/admin-users/` and `src/app/admin/users/page.tsx` |
| add a repo method | interface in `src/data/access/repos/<name>.ts`; arrow-property method in `src/server/repos/<name>.ts` wrapped in `guard` with `requireAdmin`/`branchFilter` and `writeAudit` for writes; registry entry (kind, access, zod tuple) in `src/server/rpc/<name>.ts`; name reads get/list/count/current so `kindOf` (`src/data/remote/rpcClient.ts`) classifies them | `ServerUserRepo.setUserActive` in `src/server/repos/users.ts` + `src/server/rpc/users.ts` |
| add a table or column | schema file in `src/server/db/schema/`, export it from `src/server/db/schema/index.ts`, run drizzle-kit generate and commit `drizzle/` (migrations are serial; the check fails on drift) | `src/server/db/schema/advisors.ts` |
| add a question | `QUESTIONNAIRE_V2` in `src/domain/questionnaire.ts` (data only; a new version also needs its questionnaires row, installed by `initAdmin` (`scripts/admin.ts`) / `clearFeedback` (`scripts/adminClear.ts`), and a new draft key in `src/features/feedback-form/draft.ts`); weight it in `ADVISOR_WEIGHTS` (`src/domain/metrics/advisorScore.ts`) if it should count for advisors | existing Q1 / Q1a entries |
| add a question type | new field component in `src/features/feedback-form/`, one entry in `FIELD_REGISTRY` (`src/features/feedback-form/fieldRegistry.tsx`), type in `src/domain/questionnaire.ts` | `src/features/feedback-form/RatingField.tsx` |
| add an audit action | `AuditAction` in `src/domain/types.ts` and its schema in `src/domain/schemas.ts`, label in `ACTION_LABELS` (`src/features/admin-audit/auditFormat.ts`), write it with `writeAudit` | user.create in `src/server/repos/users.ts` |
| add a KPI or block | `src/domain/metrics/overview.ts` (+ type in `src/domain/types.ts`), a tile in `KpiTiles` or a block in `OverviewBlocks` (`src/features/admin-overview/`) | the "Callbacks requested" tile in `src/domain/metrics/overview.ts` + `src/features/admin-overview/KpiTiles.tsx` |
| add a daily housekeeping step | a batch step in `src/server/jobs/cleanup.ts` (`runDailyCleanup`), counted in its summary audit row | the purge step in `src/server/jobs/cleanup.ts` |
| clear all feedback on a dev/preview database (CR-2 cut-over) | nothing to edit: pnpm admin clear-feedback --confirm-delete-all-feedback (`clearFeedback` in `scripts/adminClear.ts`) deletes alerts, responses, links, visits and old questionnaires in one transaction, installs v2 and writes one system.cleanup audit row; it refuses on production and without the flag | `tests/unit/server/admin/clearFeedback.test.ts` |
| set up a fresh database | pnpm db:migrate (`scripts/migrate.ts`), then pnpm admin init with a name and email (`initAdmin` in `scripts/admin.ts`) prints a one-time password; before launch pnpm golive:check (`scripts/golive-check.ts`) | `docs/DEPLOY.md` |

## 5. Tests
- **Unit (Vitest, jsdom):** `tests/unit/<area>/`. Server repos run against a real in-process Postgres: `createTestDb` (`tests/support/pglite.ts`) migrates a fresh PGlite, and `makeServerCtx` (`tests/support/serverCtx.ts`) wraps it in a `RequestCtx` with a `MutableClock`, `FakeCookies` and a captured log; `seedBranch` and `seedUser` add rows. Pattern: `tests/unit/server/alerts/alertRepo.test.ts` (make a context, sign in as a role, call the repo, assert on the `Result` and the rows). Screens and hooks use an in-memory fake: `fakeDataAccess` and `dataWrapper` in `tests/support/fakeDataAccess.ts` (pattern: `tests/unit/foundation/hooks.test.tsx`). Domain rules: `tests/unit/foundation/domain.test.ts`, `tests/unit/domain/phase2/rules.test.ts`; questionnaire v2 on the server: `tests/unit/server/feedback/v2Rules.test.ts`; Overview v2: `tests/unit/admin-overview/overviewV2.test.ts`; transport: `tests/unit/server/rpc/handler.test.ts`, `tests/unit/remote/rpcClient.test.ts`; branch scope across every repo: `tests/unit/server/scope-matrix/scopeMatrix.test.ts`.
- **End to end (Playwright):** `tests/e2e/<feature>/`, one spec per feature, tagged with the scenario ids (S-xx). `tests/e2e/global-setup.ts` wipes a PGlite directory, migrates it and runs `initAdmin`; the server is a production build (`next start`, `playwright.config.ts`). Helpers in `tests/support/e2e.ts` (`adminCredentials`, `adminApi`, `rpcCall`, `createBranch`, `createSupportUser`) set up data through the real RPC route. Two projects: mobile-360 and desktop-1440. `tests/e2e/foundation/csp.spec.ts` fails on any CSP violation.
- **Run one test:** pnpm exec vitest run tests/unit/server/alerts/alertRepo.test.ts · pnpm exec playwright test tests/e2e/admin-users (needs pnpm build first). **Everything:** pnpm check (`scripts/check.sh`).
- Coverage: an 80% threshold on `src/domain`, `src/data`, `src/hooks` and `src/server` (`vitest.config.ts`).

## 6. Talking points
- **Interface-first data layer paid off.** Phase 1 was a browser-only demo behind `DataAccess`; phase 2 swapped in `createRemoteDataAccess` and a server implementation of the same interfaces, and the screens barely changed. Trade-off: an interface plus a class per repo, and a registry entry per method.
- **One door, checked once.** Every call goes through `handleRpc`: same origin, known method, zod arguments, session, flood limit, then `guard`, which turns any exception into SAVE_FAILED or UNAVAILABLE and logs only the error class. Repos re-check role and branch themselves, so the proxy and `RoleGuard` are never the security boundary.
- **Safe under retries and races.** Submits are idempotent by submission id (`replay` in `src/server/repos/feedback.ts`); the visit claim is a guarded UPDATE; edits and alert updates check a version (CONFLICT "Someone else changed this…"); sign-in and step-up reserve attempts under advisory locks so parallel guesses cannot pass the caps.
- **Questionnaire v2 replaced v1, not beside it (CR-2).** No real customer data existed yet, so instead of mapping old answers the team cleared feedback with clear-feedback and made v2 the only accepted set: the public submit rejects unknown or hidden answers (`findStrayAnswers`, `src/domain/visibility.ts`), and a v1 draft in a customer's browser is thrown away (`dropLegacy`, `src/features/feedback-form/draft.ts`). Trade-off: simple analytics with no version mixing, at the cost of losing the test data.
- **Privacy by construction.** Link codes are stored only as hashes; erasure (`eraseJobCards`, `src/server/erasure.ts`) nulls personal fields, strips free text and redacts audit values through a database trigger that otherwise forbids changing the log; the erasure journal lets a restore re-apply erasures (`reapplyErasures` via `scripts/admin.ts`).
- **A problem we hit.** Sign-in took 3–4.5 s on the first preview because functions ran in the US and the database in Singapore; pinning functions to the same region fixed it (D-28). Another: staff sharing one branch connection tripped the anonymous flood limit, so a valid session now skips it (D-32).
- **With more time.** Align the advisor.rename audit action with its label, page the capped lists, rename the q12 list field, measure the password-hash cost on production, and drop the last phase-1 stub (`unavailable` for listFreshJobCards). See `docs/PRODUCTION.md`.
